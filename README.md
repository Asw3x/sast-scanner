# sast-scanner

Статический анализатор исходного кода: сигнатурный и эвристический поиск утечек учётных данных,
SQL-инъекций, выполнения команд ОС и слабой криптографии. Ядро отделено от интерфейса,
пользовательские правила подгружаются из XML без пересборки.

## Архитектура

```
SecurityLib/        ядро: не знает ни про интерфейс, ни про файлы
  AnalyzerEngine    прогон правил по тексту, выдача находок
  ScannerRule       правило: id, заголовок, severity, risk, шаблон,
                    regex или подстрока, регистр, только-в-deep-scan
  BugReport         находка: правило, severity, номер строки, фрагмент
UI (WinForms)       ввод кода, таблица результатов
```

Разделение сделано намеренно: ядро переносится в консольную утилиту или шаг CI без изменений.

## Встроенные правила

| id | что ищет |
|---|---|
| `SAST-001` | присвоения вида `password` / `secret` / `token` / `apikey` / `connectionstring` — в кавычках и без |
| `SAST-002` | конкатенация пользовательского ввода в SQL-запрос |
| `SAST-003` | запуск процессов с неконстантными аргументами |
| `SAST-004` | слабая криптография и небезопасная сериализация (только в режиме Deep Scan) |

## Пользовательские правила

```xml
<Rules>
  <Rule id="CUSTOM-001" title="Захардкоженный внутренний адрес"
        severity="Medium" risk="5" regex="true" ignoreCase="true" deepScanOnly="false">
    <Pattern>https?://(10|192\.168)\.[0-9.]+</Pattern>
  </Rule>
</Rules>
```

Готовый набор — [`examples/rules.xml`](examples/rules.xml): внутренние адреса, отключённая
проверка TLS-сертификата, небезопасная десериализация, вызов нативной библиотеки без полного пути.

## Проверить, что работает

1. Открыть `src/WindowsFormsApp1.sln` в Visual Studio, собрать, запустить.
2. Вставить в поле ввода [`examples/vulnerable.cs`](examples/vulnerable.cs).
3. Подгрузить [`examples/rules.xml`](examples/rules.xml), включить Deep Scan, нажать разбор.

Каждая помеченная комментарием строка файла должна дать находку, метод `Add` — ни одной.

## Ограничения

Анализатор сигнатурный: смотрит на текст, а не на поток данных. AST не строит, taint от
источника к стоку не отслеживает, поэтому `query(userInput)` и `query(constant)` для него
одинаковы — отсюда и ложные срабатывания, и пропуски.

Для реального поиска уязвимостей в большом проекте нужен Semgrep или CodeQL. Этот инструмент
полезен как быстрый первый проход и как разбор того, из чего такой анализатор состоит внутри.

Развивать стоит в сторону taint-анализа хотя бы в пределах одного метода: без него это grep
с удобным выводом, а не SAST.
